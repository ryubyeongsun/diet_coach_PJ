# AvoFit 면접 준비

답변은 현재 코드와 본인의 실제 경험을 기준으로 조정합니다. 팀 전체 기능과 본인 기여, 프로젝트 당시 구현과 후속 개선을 구분합니다.

## 1. 본인이 담당한 부분은 무엇인가요?

장보기 상품 추천 백엔드와 구매 수량 계산, Three.js 3D 아바타 초기 웹 연동을 담당했습니다. 식단 재료명을 정규화하고 예산·용량·재료명으로 상품 후보를 평가했습니다. 3D 모델은 전달받은 GLB 자산을 웹에 연결했으며 모델링 자체를 수행한 것은 아닙니다. 프로젝트 종료 후에는 식단 생성의 실행 자원을 전용 Executor로 분리했습니다.

근거: `ShoppingServiceImpl`, `ProductScorer`, `ProductWeightParser`, `Character3D.vue`, `AsyncConfig`.

## 2. 상품 검색을 단순 키워드 매칭으로 끝내지 않은 이유는?

식단의 재료명에는 수량·단위가 섞이고 쇼핑몰 제목에는 묶음·포장 정보가 들어갑니다. 검색어 정규화와 카테고리·상품명 필터링을 거친 뒤, 재료 적합도와 구매비용을 함께 평가했습니다. 후보가 충분할 때 AI로 의미를 보완하지만 최종 비용은 규칙으로 다시 확인합니다.

주의: 모든 후보가 점수 단계에서 탈락하면 원래 검색 결과를 재사용하는 경로가 남아 있습니다. 필터가 항상 보장된다고 답하면 안 됩니다.

## 3. 구매 수량과 예산은 어떻게 계산하나요?

상품명에서 포장 용량을 추정하고 `ceil(필요량 / 포장 용량)`으로 구매 개수를 계산합니다. 1,200g이 필요하고 포장이 500g이면 3개입니다. 개별 후보의 예산 가드는 배정 예산의 125%, 전체 장보기 검증은 115%를 사용합니다. 전체 초과 시 비싼 항목을 제외하므로 필요한 재료가 모두 추천된다는 보장은 없습니다.

주의: 임계값은 현재 구현 정책이며 최적값으로 검증한 수치는 없습니다. 용량이 없으면 1개를 기본값으로 쓰고 배송비는 반영하지 않습니다.

## 4. 파서에서 어떤 오류를 발견하고 검증했나요?

이번 정리에서 `lb`보다 `l`을 먼저 매칭하는 정규식 때문에 `1lb`가 1,000g으로 계산되는 오류를 재현했습니다. `lb`를 먼저 매칭하도록 순서를 바꾸고 453g을 반환하는 회귀 테스트를 추가했습니다. 기존 kg·g·ml·L·oz·묶음 계산 테스트도 함께 확인했습니다.

주의: 과거 프로젝트 당시에 해결한 경험과 이번 후속 수정을 구분합니다. 쉼표 천 단위, 복합 묶음, 액체 밀도 문제까지 해결했다고 말하지 않습니다.

## 5. 비동기는 무엇을 개선했나요?

첫 7일을 먼저 반환하는 구조는 기존에 있었습니다. 2026.08.15에는 공용 풀에 중첩된 작업을 넣는 구조를 전용 Executor의 한 작업 안에서 구간별로 순차 처리하도록 정리했습니다. 외부 호출이 긴 작업의 실행 자원과 처리 순서를 명시한 개선입니다. 응답 시간·TPS 개선율은 측정하지 않았습니다.

## 6. Core 5 / Max 10 / Queue 50은 어떻게 동작하나요?

코어 스레드를 사용한 뒤 작업을 큐에 넣고, 큐가 차면 최대 스레드까지 확장합니다. 모든 요청이 곧바로 10개 스레드에서 실행되는 것은 아닙니다. 최대 스레드와 큐가 모두 차면 작업 제출이 거절될 수 있습니다. 수치는 부하 테스트로 적정성을 검증해야 합니다.

## 7. 비동기 작업에 트랜잭션이 이어지나요?

요청 스레드의 Spring 트랜잭션은 다른 스레드로 자동 전파되지 않습니다. 현재 코드는 원래 트랜잭션 커밋 전 작업을 제출하고, 백그라운드 저장을 일괄 트랜잭션으로 묶지 않습니다. 커밋 후 작업 제출, 구간별 원자적 저장, 실패 상태와 재시도 설계가 다음 과제입니다.

## 8. 인증이 있으면 다른 사용자 데이터도 안전한가요?

JWT 인증은 요청자의 신원 확인이고, 특정 식단·체중에 접근할 권한은 소유권 검증으로 별도로 확인해야 합니다. ID를 입력받는 여러 경로에 소유자 비교가 없어 후속 보완이 필요합니다. 안전한 서비스라고 과장하지 않고 타 사용자 접근 회귀 테스트와 서비스 계층 검증을 개선 순서로 설명합니다.

## 9. 캐시를 Redis로 바꾸면 무엇이 달라지나요?

현재 로컬 메모리 캐시는 서버마다 별도로 존재하고 재시작 시 사라집니다. 여러 인스턴스에서 결과를 공유하려면 공유 저장소가 필요합니다. Redis 전환 시에도 키·TTL·무효화·장애 시 대체 경로·직렬화 정책을 함께 설계해야 합니다. 현재 Redis를 구현했다고 답하지 않습니다.

## 10. 지금 다시 만든다면 무엇부터 바꾸겠나요?

데이터 보존과 리소스 소유권, 비동기 저장의 정합성을 먼저 검증합니다. 그다음 상품명 경계 사례와 추천 대체 경로를 테스트하고, 생성 상태 API·재시도·BMI 정책 통일을 보강합니다. 테스트로 확인한 범위와 실제 외부 API·DB 통합 검증 범위를 구분해 설명합니다.
